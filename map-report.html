1. MAP 전략 해석왜 이 방향으로 전환했는가

과제의 MAP(Minimum Awesome Product) 정의는 명확합니다 — 기능만으로는 이미 포화된 시장에서 선택받을 수 없다. 취업 포털은 잡코리아·사람인·원티드가 이미 장악한 레드오션이므로, 본 프로젝트는 MVP < MAP 전략을 택했습니다.

따라서 전환 목표를 기능 추가가 아니라 세 가지 체감 품질로 정의했습니다:

  • ① 첫인상 — 탭 제목·파비콘·통일된 디자인 언어로 "진짜 서비스"처럼 보일 것
  • ② 정직성 — 화면에 보이는 모든 숫자와 버튼이 실제 계산·실제 동작일 것 (장식 요소 제로 지향)
  • ③ 끊김 없는 흐름 — 목록→상세→북마크→지원관리→자소서가 하나의 상태로 이어질 것

디자인 언어 보존

배포 데모는 Figma export를 픽셀 단위로 유지 — 색상 토큰·타이포·컴포넌트·레이아웃이 시안과 동일하며, 교체한 것은 오직 값과 동작입니다.

값의 출처가 명확

시안의 고정 숫자(92점·84건·배지 3)를 모두 걷어내고, matchJob / scoreResume / keywordCoverage가 매번 계산한 값으로 표시합니다. 구현체(jobfilter-web)와 같은 로직을 포팅했습니다.

추적 가능한 이력

29개 커밋이 기능 단위로 쌓여 있고, changes.html이 화면별 "시안 대비 동작"을 표로 대조합니다 — 계획·디자인·구현의 대응 관계를 어느 시점에서든 검증할 수 있습니다.

6. 동작 아키텍처정적 HTML이 "앱처럼" 동작하는 이유

demo-data.js — 엔진

window.JF 단일 소스. 스킬 사전(90+ 표면형→표준 표기), matchJob·matchJobWith 매칭, scoreResume 규칙 채점(분량·수치·STAR·JD키워드·문장장), 칸반·이력·북마크 상태. Next.js 구현체의 로직을 그대로 포팅해 같은 입력이면 같은 점수.

app.js — 공용 쉘

네비게이션·헤더 검색·알림 벨·아바타 메뉴·토스트·모바일 대응(960px↓ 상단 네비)을 16개 페이지에 일괄 제공. 아이콘 리거처 → 인라인 SVG 치환으로 캡처 호환성 확보.

demo.js — 페이지 글루

화면별 하이드레이션: 정적 DOM을 JF 실측값으로 갱신하고 이벤트를 연결. 시안 구조를 건드리지 않고 데이터만 주입하는 방식이라 디자인 보존과 기능 동작이 공존합니다.

공유 상태 — 페이지를 넘나드는 하나의 데이터 (localStorage jf-*)

북마크(jf-bookmarks) · 칸반 보드+체크리스트(jf-kanban) · 상태 이력(jf-status-history) · 자소서 초안/버전 · 프로필 스킬 · 기업 등록 공고 · 승인 상태 · 커스텀 사전.
예: s14에서 카드를 면접으로 옮기면 → 이력 기록 → s10 KPI·s81 퍼널·알림 벨이 같은 데이터로 갱신됩니다. 페이지를 넘겨도 숫자가 어긋나지 않습니다.

8. 한계와 향후 계획정직한 범위 선언

현재 한계

  • · 상태는 localStorage 기반 — 브라우저당 독립, 서버 동기화 없음 (학교 데모 범위에서 의도된 선택)
  • · 알림은 데이터가 있는 공고·이력에서만 생성 — 외부 푸시/메일 없음
  • · Figma 파일의 캡처 페이지는 픽셀 이미지 — 네이티브 레이어 편집은 제한적
  • · Next.js 구현체는 별도 로컬 시연 — 이번 배포는 정적 데모

MAP v.2 후보

  • · 알림 "읽음" 상태 영속 + 클릭 시 해당 화면 이동
  • · 캘린더 뷰 복원 — 마감·면접 일정을 칸반 데이터에서 생성
  • · 지원자-공고 매칭 설명(왜 이 점수인지 근거 표시)
  • · Next.js 구현체와 계정 연동 시 실서비스 전환 경로
